# Hairu

設置できる幅・奥行・高さ（cm）と予算から、楽天市場の収納家具の候補を探すWebアプリ。

公開URL: **https://ordinary-apartment.github.io/hairu/**

## 構成

ビルドツールや外部ライブラリを必要としないHTML/CSS/JavaScript（ES Modules）と、Node.js 24の取得・ビルド処理を使用しています。

```text
GitHub Actions Repository secrets
  RAKUTEN_APP_ID / RAKUTEN_ACCESS_KEY
         ↓ Actions内だけで使用
楽天市場商品検索API 20260701
         ↓ 必要な公開商品情報だけを抽出
dist/data/catalog.json + ホワイトリストの静的ファイル
         ↓ Pages artifact（保持1日）
GitHub Pages → ブラウザでサイズ・予算を絞り込み
```

GitHub Pagesは静的配信のため、ユーザーの検索ごとに秘密情報を使って楽天APIを呼び出すことはできません。本実装は**定期取得した候補をブラウザで検索する方式**です。楽天市場全体のリアルタイム検索ではありません。リアルタイム検索へ拡張する場合は、別のサーバー/APIプロキシとそのホスティングが必要です。

## API接続とセキュリティ

- エンドポイント: `https://openapi.rakuten.co.jp/ichibams/api/IchibaItem/Search/20260701`
- **Secret名は変更しません**: `RAKUTEN_APP_ID` → `applicationId`クエリ、`RAKUTEN_ACCESS_KEY` → `accessKey`リクエストヘッダー。
- Affiliate IDは送信せず、APIから返る通常の`itemUrl`にリンクします。
- 家具ジャンル`200166`に限定し、8種類のキーワードを各最大3ページ（各30件）取得。最大720件から重複・明確な部品・売切れ・税別価格を除外します。分類は取得キーワードによるものです。
- リクエストは直列で1.2秒間隔。429・5xx・通信失敗は最大3回、2秒・4秒の待機を挟んで再試行。認証エラーは再試行しません。
- SecretsはActions取得ステップにのみ渡します。ブラウザ・HTML・JS・JSON・ログ・Git履歴には出しません。生のエラー、リクエストURL、APIレスポンス全体はログに出しません。
- 公開データは必要な商品フィールドのみ。公開URLを楽天ドメインのHTTPSに制限し、商品リンクの追跡クエリ・フラグメントを削除します（画像はサイズ指定の`_ex`のみ保持）。DOMには`textContent`で文字列を挿入します。CSPは同一オリジンのスクリプト・通信のみ許可します。
- ビルドの公開ファイルはホワイトリスト方式。最終出力にSecretsの実値・URLエンコードした値がないか検査し、含まれる場合はビルドを停止します。
- 商品カタログはGitへcommitしません。公開済みの正常なJSONを永続的な基準データとして復元し、差分更新します。取得から時間が経過しても検索・商品表示は継続します。
- 最終取得日時を画面と商品カードに表示します。カードは商品ごとの`lastUpdatedAt`を使い、取得できなかった商品の価格を新しい時刻として表示しません。購入時は楽天市場の商品ページで価格・在庫等を確認してください。

## 寸法判定

現行の公式出力仕様と、実際のAPIレスポンスの両方で、幅・奥行・高さの専用数値フィールドがないことを確認しました。実レスポンスには`itemCaption`と`attributeIds`があり、属性情報は数値の本体寸法ではありません。

`scripts/dimensions.mjs`が**商品説明に「本体サイズ」「本体外寸」「商品サイズ」などの外寸を示すラベルがあり、その直後に幅・奥行・高さの全3軸と単位が明記されている場合だけ**抽出します。日本語ラベルやW/D/H、cm/mm、全角、小数を扱います。mmはcmに換算します。推測で寸法を補いません。軸名のない`60×30×120`は順序を推測せず対象外です。

- 内寸・収納部・棚板・梱包サイズは判定に使いません。
- 単位不足・寸法不足・範囲表記・伸縮商品・複数の異なる本体サイズ・商品名との不一致・除外された突起等の判定困難な記載は「サイズ要確認」にします。
- 同じ3寸法が繰り返されている場合は1候補として扱います。
- 商品カードに幅・奥行・高さと、説明中の**根拠の記載箇所**を表示します。
- 3軸すべて入力上限以下なら「記載サイズが条件内」。サイズ超過の商品は除外。確定できない商品は「サイズ要確認」としてその後に表示（チェックボックスで非表示にできます）。
- 3寸法がそろわなくても、商品名・キャッチコピー・本体サイズを示す商品説明に明記された本体の1軸でも上限を超える場合は除外します。例えば高さ70cmに対して「幅60 高さ180」は「サイズ要確認」に残しません。日本語の軸名付き商品名等で単位が省略されている場合は家具のcm表記として読み取り、mm明記時は換算します。商品説明では本体・外寸のラベルを必須とし、内寸・梱包・棚板・部品・対応サイズは除外判定にも使いません。
- 除外専用の`dimensionBounds`は明記された候補の最小値と根拠を保持します。複数候補でどれかが上限以下なら「サイズ要確認」のまま、全候補が上限超過なら除外します。不明の候補や読み取れない選択肢があれば、その軸を確定扱いしません。幅の選択肢が複数でも、全候補に共通する高さ180cmは無視しません。除外用の部分寸法が上限内でも、3寸法が確定していない商品を適合扱いにはしません。
- 「サイズ要確認」の候補でも、部分寸法の根拠を「確認できた寸法の記載」で表示します。数値を推測したり、画像から寸法を生成したりはしません。
- 商品説明に別々の本体サイズ候補が明記されている場合は、候補ごとの寸法を`dimensionOptions`で保持します。「候補Aは幅超過、候補Bは高さ超過」のように全候補が不適合なら除外します。候補間の幅・高さを組み合わせて架空の小さい商品を作りません。不明な候補や、より小さい寸法を示す別の信頼できる記載がある場合は、その可能性を残します。
- 自動抽出であり設置を保証しません。商品ページで選択サイズ・外寸・扉の開閉・搬入経路を確認してください。
- 予算は税込の商品価格で判定（送料別）。SKU等で価格に幅がある商品はAPIの購入可能価格上限を使って絞り込み、カードには価格範囲を表示します。

## 更新・差分管理

- 通常の商品探索は毎月1日12:17（日本時間、cron `17 3 1 * *`）。8キーワード×最大3ページで新商品を探し、今回取得できた既存商品も更新します。
- 今回の探索に現れなかった既存商品は`itemCode`で個別に確認します。探索は上位ページの限定取得なので、検索ページにないだけでは消失としません。
- セール時は`Update Hairu catalog`を手動実行し、`mode=prices`を選択します。既存商品の更新だけを行い、新規商品は追加しません。60商品以上では最大24回の検索を一括更新に利用し、結果のうち既存コードだけを取り込み、未取得の既存コードを個別確認します。60商品未満は個別照会のみです。セール期間を自動推測しません。日次scheduleを後から有効化する場合はcronを追加し、そのscheduleを`prices`に振り分けます（workflow内のコメント参照）。
- [現行API](https://webservice.rakuten.co.jp/documentation/ichiba-item-search)の`itemCode`検索は1商品を指定します。692商品なら価格更新は692回、限定探索は最大24回ですが、24回の検索では全既存商品を更新・消失確認できません。そのため一括取得＋未取得コードの個別確認を採用しました。今回の実API検証では24回で既存692商品をすべて再取得でき、個別照会は不要でした。検索結果が変わっても未取得商品の個別確認で更新漏れを防ぎます。月次も再取得したコードの個別確認を省略します。直列1.2秒間隔、リトライは別途です。
- 安定した`itemCode`を`id`に使い、名前、価格、価格帯、URL、画像、送料、店舗、販売状態を更新します。実在する売切れ商品（`availability=0`）はデータに保持し、検索候補からは外します。
- 商品ごとに`firstSeenAt`、`lastSeenAt`、`lastUpdatedAt`（情報取得）、`lastCheckedAt`（確認）を保持します。旧カタログ移行時の初回日時は従来の`generatedAt`を基準とします。
- 商品名・キャッチコピー・説明のSHA-256を`dimensionSourceHash`に保存します。元情報と寸法パーサーのSHA-256が同じ場合だけ寸法・部分寸法・候補・理由を再利用し、変更時は再解析します。説明全文は保存・公開しません。
- 新着用の`firstSeenAt`、価格変更用の`previousPrice` / `priceChangedAt`、消失確認用の`missingChecks` / `saleEndCandidate`を保持します。UI追加はありません。
- 個別検索で見つからなかった商品も削除しません。正常に完了した更新で2回連続して個別確認できなければ販売終了「候補」とします。販売終了の確定扱いはせず、既存価格・寸法・最終取得日時を保持します。再取得できれば候補を解除します。
- API検索の一部失敗・全失敗・認証失敗・不正な個別商品・全体が空の更新では処理全体を中止し、最後に公開した完全なカタログとサイトを保持します。空や部分データは公開しません。JSONを一時ファイルに書き、完全な検証・秘密情報検査の後にrenameし、全ステップ成功後だけPagesへ公開します。
- 基準データの復元に失敗した場合もデプロイを停止します。更新成功時には90日保持のバックアップartifactも保存します。通常の復元元は公開カタログなので、artifactの期限だけで基準データが消えることはありません。
- 両公開workflowは同じconcurrency groupで直列化し、互いのカタログを古い状態で上書きしないようにします。

## 入力とエラー時の動作

- 数値欄は`type=text`。寸法は`inputmode=decimal`、予算は`inputmode=numeric`でモバイルの数値キーボードを指定します。スピナーやホイールによる数値増減がなく、スクロールイベントを妨げません。
- nativeのrequired / patternと`setCustomValidity`を使い、寸法0.1〜1000cm・小数第1位、予算1〜999999999円の整数を検証します。既存ラベルと検索条件の数値検証も維持しています。
- 取得成功で条件0件: 条件を変更する案内を表示します。
- JSON読込失敗・形式不正: 通信エラーと再読み込みボタンを表示します。すでに正常なカタログを読み込めている場合はそれを保持します。
- 商品画像の読込失敗: 画像の代替テキストを表示します。

## 開発・検証

Node.js 24以上とPython 3を使用します。アプリの実行時依存はありません。ブラウザ検証には開発用のPlaywrightを使います（Macではインストール済みChrome、CIではChromium）。

```sh
cd /Users/hirabayashi/Desktop/hairu
npm test
npm ci
npm run test:ui
node scripts/build.mjs --offline
npm run preview
# http://localhost:4173
```

ローカルのofflineビルドはAPI未接続の表示を検証するものです。本物の商品データの取得には、Repository secretsを使うActionsを実行してください。Secretsをコマンド引数やローカルファイルに書く必要はありません。

CIは寸法抽出、3軸・予算の境界、価格範囲、並び順、0件、古いデータの継続検索、差分更新、寸法再利用、URL安全性、API認証送信、リトライ、全失敗・部分失敗、出力への秘密情報混入を検証します。PlaywrightでPC・スマートフォン・タブレット幅の入力・検索・並び順・根拠表示・0件・通信復旧・古いデータの検索・スピナー不在・手入力・ホイール操作・ページスクロール・HTML挿入防止・追加表示を検証します。PR検証にはSecretsを渡しません。

`npm run test:live`は公開URLの実カタログを使い、3画面幅の検索・寸法根拠・0件・横スクロールがないこと・ブラウザから楽天APIを直接呼ばないことを読み取りのみで検証します。幅60.3cm・奥行60.2cm・高さ70cmでも検索し、従来「サイズ要確認」に残っていた明確な高さ180cmの商品が、追加表示を含む全結果から除かれていることを検証します。

## GitHub Pagesと運用

公開元は**GitHub Actions**です（初期状態のmain/rootから変更）。ソースは引き続きmainのrootに配置しますが、商品データをGit履歴に残さずPages artifactで配信するため、branch/root方式ではなくActions方式を採用しています。

- `.github/workflows/deploy.yml`: mainへのpush / 手動 → テスト → 公開済みカタログ復元 → 静的サイトのビルド・公開。楽天APIは呼びません。
- `.github/workflows/catalog.yml`: 月次 / 手動 → テスト → 基準復元 → 差分更新 → バックアップ → Pages公開。手動の`discovery`と`prices`を選択できます。
- `.github/workflows/test.yml`: push / PRのSecrets不要検証。
- `.github/workflows/probe.yml`: 手動のAPI接続・レスポンス観測用。観測artifactは1日で削除されます。
- GitHubのscheduleは遅延・停止する場合があります。長期無活動による無効化もあるため、Actions実行状況を確認してください。更新停止中も公開済みカタログの検索は継続します。
- カタログ件数の増加に伴い個別更新の呼出回数・所要時間は増えます。現状は60分のジョブ上限、直列処理です。大量化した場合は対象分割・取得方式の見直しが必要です。
- 今回指定された月次更新・古い価格の継続表示と、[楽天の公式キャッシュ・更新案内](https://webservice.faq.rakuten.net/hc/ja/articles/900001974343)には差があります。同案内は価格・在庫のキャッシュ制限と週1回以上の更新を示しています。継続運用には楽天側の利用条件の確認・調整が必要です。日時・価格確認の注意書きだけで条件適合を保証するものではありません。
- 公開カタログは限定的な候補です。0件は楽天市場全体に該当商品がないことを意味しません。自動寸法抽出は厳しめのため未判定の商品もあります。
